# Acceptance status

## Qualified milestone, not whole-product completion

An existing developer agent can run the exact included synthetic React/TypeScript host through `assess → plan → approve → apply → deliver → delivery-check`. One explicitly approved, versioned verification profile covers its bounded execution. The resulting bundle binds the original/candidate, plan, approval, recipe, verification and evidence bytes; `complete` names only that profile's scope.

Actual evidence includes original/generated typechecks and Vite builds, ten business baseline/differential cases, real HTTP authorization and one approved mutation, and real sandboxed Chromium interactions. Completion additionally requires observed zero process exit, no timeout/signal and confirmed owned-service/process cleanup. Missing tools produce partial/not-run; failed checks and interrupted runs cannot become complete from a child-supplied PASS. The baseline-ordering implementation passed the strict build and 188-test aggregate and a real browser member/assignee journey. [Evidence and limits](verification/delivery-qualification.md).

Separate evidence qualifies opt-in PostgreSQL/DBOS recovery, immutable release behavior and default-OFF/explicit-ON business improvements. Those results are not imported as proof that this particular delivery profile exercised them. The repeatable profile uses a deterministic simulated model and memory runtime. Production identity, real-provider quality/costs, arbitrary host support and a general execution sandbox are not claimed.

The approved [plan §15.1 and §16](../IMPLEMENTATION_PLAN.md) is broader than the fixed profile:

- **Baseline timing, closed for this fixture:** profile apply archives the trusted original before patching, with a one-use core receipt and a bound source/plan/approval/collector chain. - **Planned business breadth, closed for the fixed fixture:** ticket reads, member queries, priority and assignee changes now have pre-apply baseline/differential, permission/approval and real HTTP/browser evidence. A separate same-session durable member query → assignee approval → lost response → process death → receipt reconciliation test passed without redispatch. Neither fixture qualifies arbitrary host mappings or real-provider behavior.
- **Combined acceptance:** the new durable assignee session used a static release ID. Next qualify it through persistent HTTP with a published release, then capability removal/new-release filtering versus an old bound approval across restart, selected behavior OFF/ON and release rollback. The existing HTTP-PG harness now explicitly registers its supported member catalog, but that separate suite was not rerun in this member milestone. Independent green component reports do not prove the whole combination.
- **Assignee UI fault coverage:** the new browser assignee journey proves a fresh-context normal approval. Refresh/disconnect/cancel while that assignee approval is pending remains unrun; old priority UI evidence is not a substitute.
- **Remaining fault coverage:** follow the plan's negative matrix, including actual disconnect/cancel/recovery boundaries. The new delivery terminal reducer has unit negative tests and observed SIGKILL failure handling; deliberate timeout/cleanup-hang OS fault injection is still unrun.

These are engineering/acceptance gaps, not a request for the user to approve each ordinary implementation step again.

## After that: repeatability and release readiness

Before declaring AE itself accepted and moving to the three external cases, reconcile the remaining approved milestone gates:

1. **Cross-stack beta (§15.2):** a genuinely different non-React/non-TS host produced by AE's lifecycle with its own business baseline/acceptance; the planned Java/Spring adapter and authenticated remote MCP qualification; source-drift/idempotency/rollback, clean installation, version diagnostics, upgrade and uninstall checks. Generic manifest detection alone is not this result.
2. **Release candidate (§15.3 and §16.1):** reproducible clean installation; schema/old-run upgrade and backup-restore qualification; data retention/deletion and isolation; release configuration/rollback; security, license/SBOM, operational guidance and honest support coverage. Applicable knowledge, automation, A2A and mobile/mini-app work must retain its exact implemented/contract-only/not-run scope rather than a blanket platform claim.
3. **Evidence-backed acceptance:** record each applicable exit gate as pass/fail/not-run/blocked against the actual candidate. Any deliberate scope change must be explicit, not inferred from a passing fixture. Real-provider tests or production actions still need their specific budget, environment and permission; this status does not authorize paid calls or deployment.
